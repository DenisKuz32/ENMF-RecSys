# Отчёт по проекту: рекомендательный алгоритм ENMF

**Задача.** Реализовать на PyTorch рекомендательный алгоритм на основе
матричного разложения с неявной обратной связью, обучаемый на CPU и GPU, и
сравнить его с бейзлайном по популярности по метрике NDCG@K.

**Алгоритм.** ENMF — Efficient Neural Matrix Factorization without Sampling
(Chen et al., ACM TOIS 38(2), 2020).

---

## 1. Постановка задачи

Дан набор взаимодействий пользователь–объект без явных оценок: факт
взаимодействия считается положительным сигналом, отсутствие взаимодействия —
не отрицательным сигналом, а **отсутствием информации**. В этом и состоит
специфика implicit feedback: непросмотренный фильм мог не понравиться, а мог
просто не попасться на глаза.

Требуется для каждого пользователя выдать K наиболее релевантных объектов из
каталога, ранжируя по предсказанной релевантности.

Используется **user-based** вариант, как того требует задание: в MovieLens-1M
пользователей (6 040) больше, чем объектов (3 416), поэтому батчи формируются по
пользователям, и матрица Грама по пользователям считается по батчу, а по
объектам — по всему каталогу.

## 2. Архитектура решения

### 2.1 Модель

Предсказание релевантности:

```
y(u, i) = hᵀ (p_u ⊙ q_i)
```

где `p_u ∈ ℝᵈ` — эмбеддинг пользователя, `q_i ∈ ℝᵈ` — эмбеддинг объекта, `⊙` —
поэлементное произведение, `h ∈ ℝᵈ` — обучаемый вектор весов предсказательного
слоя. При `h = 1` выражение вырождается в классическое матричное разложение;
обучаемый `h` позволяет модели взвешивать латентные компоненты по-разному, и это
вся «нейронность» архитектуры.

Обучаемые параметры: `P ∈ ℝ^{|U|×d}`, `Q ∈ ℝ^{|I|×d}`, `h ∈ ℝᵈ`.

Dropout применяется к эмбеддингу пользователя. Для объектов заведён
дополнительный паддинговый эмбеддинг с нулевым вектором — он нужен для
батчирования историй разной длины (см. 2.4).

### 2.2 Функция потерь: обучение без сэмплирования

Это главный элемент подхода и основной объём работы в проекте.

Классический взвешенный квадратичный лосс по **всем** парам:

```
L = Σ_u Σ_{i∈I} c_ui · (y(u,i) − y_ui)²
```

где `y_ui = 1` для наблюдённых пар (вес `c⁺`), `y_ui = 0` для всех остальных
(вес `c⁻`, обычно много меньше `c⁺`). Прямое вычисление стоит `O(|U|·|I|·d)` —
для реального каталога неподъёмно, из-за чего обычно прибегают к негативному
сэмплированию. Авторы ENMF показывают, что сэмплирование неустойчиво и мешает
достичь оптимума, и предлагают считать полную сумму точно, но дёшево.

**Шаг 1.** Разделяем сумму и добавляем-вычитаем наблюдённую часть с
отрицательным весом, чтобы вторая сумма шла по всему каталогу:

```
L = Σ_u Σ_{i∈R_u} [ c⁺(y − 1)² − c⁻y² ]  +  Σ_u Σ_{i∈I} c⁻ y²
```

Первое слагаемое идёт только по наблюдённым взаимодействиям — это `O(|R|·d)`.

**Шаг 2.** Раскрываем второе слагаемое. Так как `y(u,i) = Σ_k h_k p_uk q_ik`,

```
y(u,i)² = Σ_k Σ_l h_k h_l p_uk p_ul q_ik q_il
```

и суммирование по `u` и по `i` **расщепляется**:

```
Σ_u Σ_i c⁻ y²  =  c⁻ · Σ_{k,l} [ h_k h_l · (Σ_u p_uk p_ul) · (Σ_i q_ik q_il) ]
               =  c⁻ · sum( (h hᵀ) ⊙ (Pᵀ P) ⊙ (Qᵀ Q) )
```

Вместо перебора `|U|·|I|` пар достаточно двух матриц Грама размера `d × d`.

**Шаг 3.** Раскрываем квадрат в первом слагаемом:

```
c⁺(y − 1)² − c⁻y² = (c⁺ − c⁻) y² − 2c⁺ y + c⁺
```

Константа `c⁺·|R|` не зависит от параметров и в реализации отброшена. Побочный
эффект оказался полезным: для паддинговых позиций `y ≡ 0` (паддинговый
эмбеддинг нулевой), и их вклад в оставшееся выражение тоже равен нулю — маска
при вычислении лосса не нужна вовсе.

**Итоговая сложность.** По всем данным сразу — `O(|R|·d + (|U| + |I|)·d²)`
вместо `O(|U|·|I|·d)`: перебор всех пар заменён построением двух матриц Грама.
В нашем мини-батчевом обучении шаг на `B` пользователях стоит
`O(|R_B|·d + (B + |I|)·d²)` вместо `O(B·|I|·d)`: матрица `QᵀQ` пересчитывается
на каждом шаге, потому что параметры меняются. На ML-1M (`B = 256`, `d = 64`)
это около 17.5 млн умножений против 56 млн на шаг, то есть выигрыш примерно в
`B/d` раз; главное же — стоимость больше не содержит произведения `B·|I|`, и
матрицу скоров `B × |I|` строить не нужно.

### 2.3 Проверка корректности лосса

Формула выведена вручную, поэтому ей нельзя доверять без проверки: ошибка в
такой формуле не приводит к падению — модель обучается и выдаёт правдоподобные
метрики, просто оптимизирует не то.

Поэтому реализована вторая, наивная версия лосса — прямое вычисление по полной
матрице `[B, |I|]` без каких-либо преобразований — и обе версии сверяются в
тестах:

* совпадение значений при `neg_weight ∈ {0, 0.01, 0.1, 0.5, 1.0}` и
  `pos_weight ∈ {0.5, 1.0, 2.0}` — расхождение менее `1e-9` (double precision);
* совпадение **градиентов** по всем трём группам параметров — расхождение менее
  `1e-9`;
* паддинг не влияет ни на значение, ни на градиенты;
* паддинговый эмбеддинг остаётся нулевым после шагов оптимизации.

Наивная версия сохранена в коде (`enmf.losses.enmf_loss_naive`) как
исполняемая спецификация: она документирует, что именно оптимизируется.

### 2.4 Батчирование

Один элемент датасета — это **один пользователь со всей его историей**, а не
одна пара (пользователь, объект). Истории имеют разную длину и дополняются
паддинговым индексом до максимума **в батче**, а не по всему датасету: в
MovieLens-1M самый активный пользователь имеет более двух тысяч оценок при
медиане около сотни, и выравнивание по глобальному максимуму раздуло бы батчи
на порядок.

### 2.5 Распределённое обучение (DDP)

Оба слагаемых лосса пропорциональны числу пользователей в батче: первое явно,
второе — через матрицу Грама пользователей `P_Bᵀ P_B`. Лосс делится на размер
батча, поэтому DDP-усреднение градиентов между процессами эквивалентно
обучению одним процессом на объединённом батче.

Матрица Грама объектов `Qᵀ Q` считается целиком на каждом процессе. Это
допустимо: DDP реплицирует параметры, значит на всех процессах она одинакова, а
усреднение одинаковых величин их не меняет. Стоимость — `O(|I|·d²)` на шаг.

**Найденная в процессе ловушка.** Изначально лосс обращался к методам модели
напрямую, минуя `forward`. DDP навешивает подготовку синхронизации градиентов
внутри собственного `forward`: он помечает, какие параметры участвовали в шаге,
и готовит редуктор к обратному проходу. При обходе `forward` обучение **не
падает** — оно молча превращается в несколько независимых моделей, по одной на
процесс, и проявляется лишь просадкой метрик. Решение: обёртка
`ENMFTrainingModule`, чей `forward` возвращает значение лосса; в DDP
заворачивается именно она.

Корректность проверена тестом: градиенты DDP на двух процессах с половинами
батча совпадают с градиентами одиночного процесса на полном батче (расхождение
менее `1e-8`). Отдельно проверено, что распределённая оценка (шардирование
пользователей плюс `all_reduce` сумм) даёт в точности те же метрики, что и
одиночная — усреднение средних по процессам такого свойства не имеет, если
доли разного размера.

**Когда эквивалентность точна.** Каждый процесс делит свой лосс на *свой*
размер батча, а DDP затем усредняет градиенты. Результат совпадает с
одиночным процессом на объединённом батче, только если доли батча на всех
процессах одинакового размера; при долях, скажем, 12 и 4 пользователя вес
пользователей меньшей доли оказывается втрое больше
(`tests/test_ddp.py::test_ddp_equivalence_requires_equal_shards`). В этом
проекте условие выполняется автоматически: `DistributedSampler` дополняет
список пользователей повторами до числа, кратного числу процессов, поэтому все
процессы получают одинаковое число пользователей, и при одинаковом
`batch_size` шаги на них равного размера. Цена — до `world_size − 1`
повторно обработанных пользователей за эпоху; в наших прогонах на ML-1M
обучающих пользователей кратно 2 и 4, и повторов нет
(`test_distributed_sampler_equalizes_shards`). Поэтому нормировку не меняли:
деление на глобальный размер батча потребовало бы лишнего коллективного
вызова на каждом шаге ради случая, который здесь не возникает.

**Чем DDP-прогон всё же отличается от одиночного.** `batch_size` в конфиге —
размер батча *на процесс*, поэтому при `N` процессах один шаг оптимизатора
обрабатывает `256·N` пользователей, а шагов за эпоху в `N` раз меньше. DDP
эквивалентен одному процессу с батчем `256·N`, а не с батчем 256, поэтому
метрики DDP-прогонов близки к одиночному, но не обязаны совпадать с ним
точно.

Backend выбирается автоматически: `nccl` при CUDA, `gloo` на CPU и Intel XPU.
В данной работе прогоны выполнялись на CPU.

## 3. Экспериментальная постановка

### 3.1 Данные

MovieLens-1M: 1 000 209 оценок. Предобработка:

1. бинаризация: факт оценки считается положительным взаимодействием
   (порог настраивается параметром `binarize_threshold`);
2. дедупликация пар (u, i) с сохранением самой ранней метки времени;
3. k-core фильтрация (по умолчанию 5) итеративно до стабилизации — удаление
   редких объектов делает редкими пользователей и наоборот, одного прохода
   недостаточно;
4. перенумерация идентификаторов в плотные индексы.

| Характеристика | Значение |
|---|---|
| Пользователей | 6 040 |
| Объектов | 3 416 |
| Взаимодействий | 999 611 |
| Плотность | 4.84% |

Пользователей больше, чем объектов, поэтому по условию задания используется
user-based вариант; это проверяется при подготовке данных и пишется в лог
запуска (`user-based вариант соответствует условию: пользователей 6040 >
объектов 3416`).

### 3.2 Разбиение по времени

Задание требует, чтобы взаимодействия из будущего относительно валидационной
части не попадали в обучающую. Реализованы две стратегии.

**`global` (основная)** — единая точка отсечения по времени для всего
датасета: последние 20% взаимодействий по времени уходят в валидацию. Условие
выполняется буквально: самое позднее обучающее взаимодействие раньше самого
раннего валидационного (проверено на ML-1M и тестом
`tests/test_split.py::test_global_split_has_no_future_leakage`).

**`per_user` (дополнительный эксперимент)** — своя точка отсечения у каждого
пользователя: последние 20% его взаимодействий уходят в валидацию. Условие
выполняется только внутри пользователя: на ML-1M 801 921 из 802 085
обучающих взаимодействий сделаны позже самого раннего валидационного, то есть
в обучение попадает «будущее» относительно валидации других пользователей.

Результаты на ML-1M (`enmf compare-splits --config configs/ml1m.yaml`,
файл `reports/splits.json`):

| | `global` | `per_user` |
|---|---|---|
| Точка отсечения | 2 декабря 2000, 14:44 UTC (`975768294`) | своя у каждого пользователя |
| Взаимодействий в train | 799 687 | 802 085 |
| Взаимодействий в валидации до фильтрации | 199 924 | 197 526 |
| Холодных пользователей (нет в train) | 640 | 0 |
| Холодных объектов (нет в train) | 5 | 1 |
| Взаимодействий в валидации после удаления холодных | 104 411 | 197 521 |
| Оцениваемых пользователей | 1 143 из 1 783 (64.1%) | 6 040 из 6 040 (100%) |
| Отложенных объектов на пользователя (в среднем) | 91.3 | 32.7 |

Основной выбрана стратегия `global`: она буквально соответствует условию, а
1 143 оцениваемых пользователя достаточно для устойчивой оценки (разброс
NDCG@10 по трём сидам — 0.0023, см. 4.2). Цена: 640 пользователей, впервые
появившихся после точки отсечения, user-based модель оценить не может (у них
нет обученного эмбеддинга). На них приходится 95 513 валидационных
взаимодействий — почти половина. Оценка `global` — это качество рекомендаций
для пользователей, которые уже были в системе.

На других данных выбор может быть иным: на `ml-latest-small` и на нашей
синтетике `global` вырождается (на `ml-latest-small` оценимы 25 пользователей
из 122), поэтому их конфиги используют `per_user`.

Две тонкости, не влияющие на вывод, но заслуживающие упоминания:

* k-core фильтрация выполняется до разбиения, то есть по всем данным,
  включая валидационный период. Это стандартная практика, но формально то,
  какие объекты и пользователи остаются в датасете, зависит от «будущего».
* В `per_user` у части пользователей последнее обучающее и первое
  валидационное взаимодействие имеют одну и ту же секунду (6 087
  валидационных взаимодействий, 3%); какое из них куда попадёт, решает
  порядок строк в исходном файле. В `global` такого нет: отсечение идёт по
  значению времени, а не по позиции.

### 3.3 Протокол оценки

Для каждого пользователя ранжируется **весь каталог** за вычетом объектов из
его обучающей истории. Полное ранжирование, в отличие от распространённой схемы
«один позитив против 100 случайных негативов», не зависит от способа
сэмплирования негативов и не завышает метрики; так же оценивает и официальная
реализация авторов (ранжирование всех объектов с маскированием обучающих).

Временное разбиение оставляет пользователю несколько отложенных взаимодействий,
поэтому используется общая формула NDCG:

```
DCG@K  = Σ_{j=1..K} rel_j / log₂(j + 1),   rel_j ∈ {0, 1}
IDCG@K = Σ_{j=1..min(K, R)} 1 / log₂(j + 1)
NDCG@K = DCG@K / IDCG@K
```

Нормировка на `min(K, R)`, а не на `R`, принципиальна: иначе пользователь с
числом релевантных объектов больше `K` физически не смог бы получить NDCG@K = 1,
и средняя метрика зависела бы от распределения активности пользователей, а не
от качества модели.

Дополнительно считаются Recall@K и HitRate@K. Значения K: 5, 10, 20.

### 3.4 Бейзлайны

**Популярность** (требуется заданием) — неперсонализированные рекомендации:
всем пользователям предлагаются самые частые объекты обучающей выборки, за
вычетом уже просмотренных. Это обязательная точка отсчёта: модель, не
обыгрывающая популярность, бесполезна, а на MovieLens популярность — сильный
соперник (см. 4.1).

**item-kNN** (дополнительно) — классическая item-based коллаборативная
фильтрация [6] без обучения (`enmf.models.item_knn`). Два фильма похожи, если
чаще обычного встречаются в историях одних и тех же пользователей; мера —
φ-корреляция бинарных признаков «фильм есть в истории», сглаженная множителем
`n_ij / (n_ij + α)` (`n_ij` — число пользователей, у которых есть оба фильма),
отрицательные значения обнуляются. Скор кандидата — сумма его похожестей на
фильмы из истории пользователя. Все статистики считаются только по train.
Это персонализированный, но очень простой метод; простые соседские методы
нередко оказываются сильными соперниками нейросетевых рекомендательных
моделей [7], поэтому сравнение с ним проверяет, даёт ли ENMF что-то сверх
них. Настройки подобраны по валидации так же, как гиперпараметры ENMF (4.7).

Оба бейзлайна реализуют тот же контракт `full_scores`, что и ENMF, и
оцениваются **тем же самым кодом** — на тех же пользователях, с тем же
исключением просмотренного. Сравнение честно по построению.

совпадают).

## 4. Результаты

Запуск `runs/enmf_ml1m` (`enmf train --config configs/ml1m.yaml`), разбиение

| NDCG@10 | 0.2675 | 0.2765 | 0.2845 | +6.4% | +2.9% |
| NDCG@20 | 0.2522 | 0.2569 | 0.2629 | +4.2% | +2.3% |
| Recall@5 | 0.0201 | 0.0220 | 0.0281 | +39.9% | +27.6% |
| Recall@10 | 0.0370 | 0.0391 | 0.0467 | +26.3% | +19.4% |
| Recall@20 | 0.0664 | 0.0650 | 0.0777 | +17.1% | +19.6% |
| HitRate@5 | 0.5573 | 0.5713 | 0.6159 | +10.5% | +7.8% |

| HitRate@20 | 0.7577 | 0.7270 | 0.7708 | +1.7% | +6.0% |

ENMF лучше обоих бейзлайнов по всем метрикам. По NDCG выигрыш над
популярностью тем больше, чем меньше K: модель точнее всего в самом верху
списка. item-kNN лишь ненамного сильнее популярности по NDCG (0.2765 против
0.2675), а по HitRate@10 и @20 даже слабее её. Абсолютные значения
NDCG высокие, а Recall низкий из-за постановки: у пользователя в среднем 91
отложенный объект (3.2), поэтому в топ-10 легко попасть хоть во что-то
(HitRate@10 у популярности уже 0.67), а доля найденных из 91 мала.

Модель не схлопнулась и рекомендует заметно разнообразнее популярности
(`python scripts/diagnose_run.py --run runs/enmf_ml1m`,
`runs/enmf_ml1m/diagnostics.json`):

* эффективный ранг матриц эмбеддингов пользователей и объектов — 64 из 64,
  `‖h‖ = 4.06`, 28 из 64 компонент `h` положительны;
* в топ-10 хотя бы одного пользователя попадают 616 разных объектов из 3 416,
  у популярности — 137;
* при этом средний по пользователям скор объекта коррелирует с его
  популярностью на 0.99: значительная часть выученного — это популярность,
  а персонализация работает поверх неё.

Выигрыш над популярностью по NDCG@10 (0.016 в среднем, от +5.0% до +6.5% по

не объясняется случайностью инициализации. Выигрыш над item-kNN скромнее:

погрешностью порядка ±2–3 п.п.

### 4.3 Главный гиперпараметр: `neg_weight`

`python scripts/run_experiments.py --config configs/ml1m.yaml --grid neg_weight`,
зерно 42, `d = 64` (полная таблица — `reports/experiments.md`):

| `neg_weight` | NDCG@10 | к популярности | Recall@10 | Лучшая эпоха |
|---|---|---|---|---|
| 0.001 | 0.2027 | −24.2% | 0.0280 | 2 |
| 0.005 | 0.2198 | −17.8% | 0.0380 | 6 |
| 0.01 | 0.2408 | −10.0% | 0.0446 | 7 |
| 0.02 | 0.2550 | −4.7% | 0.0473 | 6 |
| 0.05 | 0.2650 | −0.9% | 0.0475 | 6 |
| 0.1 | 0.2724 | +1.8% | 0.0475 | 6 |
| 0.2 | 0.2794 | +4.4% | 0.0477 | 6 |
| 0.5 | 0.2813 | +5.2% | 0.0486 | 9 |
| 0.7 | 0.2820 | +5.4% | 0.0468 | 6 |
| **1.0** | **0.2845** | **+6.4%** | 0.0467 | 22 |

Лучшее значение — 1.0, край сетки, а отрыв от 0.5 (0.003) сопоставим с
разбросом по зёрнам. Поэтому 0.5 и 1.0 дополнительно сравнены на зёрнах 1 и 2
(`--set loss.neg_weight=<nw> train.seed=<s>`): NDCG@10 для 0.5 —
0.2813 / 0.2762 / 0.2825, для 1.0 — 0.2845 / 0.2809 / 0.2850 (зёрна 42 / 1 / 2).
1.0 лучше на каждом зерне, и это значение записано в конфиг. Значения больше
1.0 (пропущенные пары весят больше наблюдённых) не перебирались.

При `neg_weight = 1.0` веса наблюдённых и пропущенных пар равны, и лосс
превращается в обычную квадратичную ошибку по всей матрице: коэффициент
`(c⁺ − c⁻)` при `ŷ²` в слагаемом по позитивам обнуляется. Эффективная
формула ENMF при этом по-прежнему нужна: именно она делает полную сумму по
`|U|·|I|` парам вычислимой.

### 4.5 Дополнительный эксперимент: разбиение `per_user`

`enmf train --config configs/ml1m.yaml --set data.split_strategy=per_user
output.run_name=enmf_ml1m_per_user`, те же гиперпараметры, 6 040 оцениваемых
пользователей, лучшая эпоха 32.

| Метрика | Популярность | item-kNN | ENMF | ENMF к популярности | ENMF к item-kNN |
|---|---|---|---|---|---|
| NDCG@5 | 0.1155 | 0.1444 | 0.1385 | +19.9% | −4.1% |
| NDCG@10 | 0.1096 | 0.1388 | 0.1377 | +25.6% | −0.8% |
| NDCG@20 | 0.1110 | 0.1407 | 0.1473 | +32.8% | +4.7% |
| Recall@10 | 0.0375 | 0.0594 | 0.0667 | +77.6% | +12.2% |
| Recall@20 | 0.0713 | 0.0988 | 0.1203 | +68.8% | +21.8% |
| HitRate@10 | 0.4429 | 0.5487 | 0.5776 | +30.4% | +5.3% |

При разбиении внутри пользователя выигрыш над популярностью в 4 раза больше
(+25.6% против +6.4% по NDCG@10), а популярность заметно слабее (0.1096
против 0.2675). А вот item-kNN здесь силён: в самом верху списка (NDCG@5 и
@10) он немного лучше ENMF, ENMF выигрывает начиная с NDCG@20 и по полноте

любой из перебранных гиперпараметров. Цифры `per_user` выше, но получены в
постановке, которая допускает «будущее» других пользователей в обучении, —
поэтому основным результатом работы считается 4.1.

### 4.6 Масштабирование в DDP

Одинаковое число потоков на процесс (`OMP_NUM_THREADS=2`), запуски
`runs/enmf_ddp1` (`enmf train`), `runs/enmf_ddp2` и `runs/enmf_ddp4`
(`torchrun --nproc_per_node=2|4 -m enmf.cli train`). Время — медиана по
эпохам, только обучение, без оценки.

| Процессов | Секунд на эпоху (медиана) | Ускорение | NDCG@10 |
|---|---|---|---|
| 1 | 3.68 | 1.00× | 0.2845 |
| 2 | 2.44 | 1.51× | 0.2837 |
| 4 | 1.58 | 2.33× | 0.2827 |

Для сравнения: основной запуск в один процесс без ограничения потоков —
2.53 с на эпоху.

Ускорение сублинейное: 1.51× на 2 процессах и 2.33× на 4. Профилирование не
проводилось, поэтому причины ниже — гипотезы, а не измерения: на каждом шаге
все процессы синхронизируют полные градиенты эмбеддингов (605 312 параметров,
плотные градиенты), матрица Грама объектов `QᵀQ` считается на каждом процессе
целиком (закон Амдала: эта доля работы не делится между процессами), есть
фиксированные накладные расходы Python на сборку батчей.

Качество в DDP практически то же (0.2827–0.2845), но не обязано совпадать
точно: при `N` процессах один шаг обрабатывает `256·N` пользователей, шагов
за эпоху в `N` раз меньше (раздел 2.5); у `enmf_ddp4` лучшая эпоха — 15
против 22.

### 4.7 Подбор бейзлайна item-kNN

`python scripts/tune_item_knn.py --config configs/ml1m.yaml` — сглаживание
`α ∈ {0, 10, 50, 200, 1000, 5000, 20000}` × агрегация {сумма похожестей,
среднее трёх наибольших}, выбор по NDCG@10 на валидации `global`, как и для
ENMF (полная таблица — `reports/item_knn_grid.md`):

| α | Сумма, NDCG@10 | Среднее top-3, NDCG@10 |
|---|---|---|
| 0 | 0.2070 | 0.1758 |
| 10 | 0.2110 | 0.1856 |
| 50 | 0.2271 | 0.2005 |
| 200 | 0.2472 | 0.2240 |
| 1000 | 0.2682 | 0.2474 |
| 5000 | 0.2751 | 0.2561 |
| **20000** | **0.2765** | 0.2588 |

Выбраны сумма и `α = 20000` (`configs/ml1m.yaml`, секция `eval`). Это край
сетки, но кривая уже вышла на плато: от 5000 до 20000 прирост 0.0014. Чем
больше `α`, тем сильнее похожесть `φ·n_ij/(n_ij+α)` приближается к `φ·n_ij/α`,
то есть тем больший вес получают пары, встречающиеся у многих пользователей, —
а это популярные фильмы. Лучший item-kNN на `global` фактически сдвигается к
популярности, что согласуется с силой популярности в этой постановке (4.1).
Те же настройки используются и в `per_user` (4.5), так же как
гиперпараметры ENMF.

## 5. Выводы

1. **ENMF обыгрывает популярность по всем метрикам**, но умеренно: в основной
   постановке (`global`) NDCG@5/10/20 выше на 8.7/6.4/4.2%, Recall@10 — на
   26.3%, HitRate@10 — на 2.3% (4.1). Выигрыш по NDCG@10 устойчив к зерну:
   от +5.0% до +6.5% на трёх зёрнах при разбросе 0.0023 (4.2). При
   разбиении `per_user` выигрыш по NDCG@10 — 25.6% (4.5): популярность в
   «будущем» MovieLens — гораздо более сильный соперник, чем в истории
   каждого пользователя. **Над простым item-kNN выигрыш небольшой:** в
   `global` ENMF лучше по всем метрикам (NDCG@10 +2.9%, на трёх зёрнах от
   +1.6% до +3.1%, Recall@10 +19%), в `per_user` уступает ему в верху списка
   (NDCG@10 −0.8%) и выигрывает по полноте (Recall@10 +12%). Значительная
   часть качества на ML-1M достижима и без обучения модели.
2. **Оптимальный `neg_weight` — 1.0**, верхний край сетки; качество выходит
   на плато начиная с 0.2, а при `neg_weight ≤ 0.05` ENMF проигрывает
   популярности по NDCG (4.3). Оптимум того же порядка, что и значение по
   умолчанию в официальной реализации для ML-1M (0.5). Данные довольно плотные
   (4.84%), и пропущенные пары здесь лучше не «обесценивать»: на ML-1M
   выигрывает постановка, где все пары весят одинаково.
3. **Размерность: насыщения сверху нет, качество падает с ростом `d`** — от
   0.2947 при `d = 16` до 0.2728 при `d = 256`, и большие модели переобучаются
   за 5–8 эпох (4.4). Основной конфиг оставлен с `d = 64`, выбор меньшей
   размерности требует отдельной тестовой выборки.
4. **Обучение:** лосс убывает монотонно на всех 32 эпохах основного запуска,
   NDCG@10 растёт с 0.115 после первой эпохи до 0.270 к третьей, а с пятой
   держится на плато 0.273–0.285. Лучшая эпоха — 22, ранняя остановка
   срабатывает на 32-й. Лучшая эпоха выбирается как максимум зашумлённого
   плато на валидации, поэтому её значение немного оптимистично (раздел 6).

## 6. Ограничения и что можно развить

* **Нет отдельной тестовой выборки.** Одна и та же валидация используется для
  ранней остановки, подбора `neg_weight` и сравнения с популярностью, поэтому
  итоговые числа ENMF смещены вверх. Популярность ничего не подбирает, так что
  прирост к ней тоже немного завышен. Естественное развитие — третья часть по
  времени (последние ~10%) только для финальной оценки.
* **Оцениваются только «старые» пользователи.** При `global` 640 пользователей
  (почти половина валидационных взаимодействий) появились после точки
  отсечения и не оцениваются: модель чисто коллаборативная, холодный старт не
  решается. Команда `enmf recommend` для такого пользователя честно
  переключается на популярность (поле `"source": "popularity"` и
  предупреждение в логе), а не выдаёт рекомендации по необученному
  эмбеддингу.
* Реализован только user-based вариант (ENMF-U), как того требует задание для
  случая «пользователей больше, чем объектов». В статье описаны также ENMF-I
  (батчирование по объектам) и ENMF-A (чередование).
* item-kNN, как и ENMF, настраивался по той же валидации, поэтому сравнение
  двух моделей между собой честное, но обе оценки смещены вверх одинаковым
  образом.
* Разнообразие измерено лишь грубо (число разных объектов в топ-10, 4.1);
  метрики покрытия и новизны в протокол оценки не входят.
* Рекомендации строятся по всему каталогу; ранжирование произвольного набора
  объектов-кандидатов не реализовано.
* Тонкости разбиения (k-core до разбиения, совпадающие метки времени в
  `per_user`) описаны в 3.2.
